  <action>
Create set-password.html from the same shell as login.html, with noindex, title, skip link, noscript card and all regions `hidden`, no aria-current on the header, per D-08. Add it and js/set-password.js to tools/build-site.sh in the copy line and the page loops.

js/set-password.js per Pattern 2 of 07-RESEARCH.md and the UI-spec amendment:
- First statements of the script: read `token_hash` and `type` from the query, then immediately `history.replaceState` to the bare path, before any await. Hold them in local variables only.
- Accept `type` only if it is `invite` or `recovery`. A token with any other type goes to the expired view.
- Token present: show the heading for that type and the Continue button. Do NOT call verifyOtp on load, because email scanners open links in advance. The click calls `sb.auth.verifyOtp({ token_hash, type })` once. Any error shows "This link has expired" with "Send me a new link" going to `login.html#reset` and "Back to sign in", and focus moves to the heading. Any non-network error counts as expired, not on the code name, per research A4. A network failure shows the service banner with Try again, because the link may still be good.
- No token, session present: this is the change-password route. Skip Continue and show the form with the reset heading.
- No token, no session: show the expired view.
- Form: "New password" and "Type it again" with `autocomplete="new-password"`, `minlength` set from AUTH_CONFIG.PASSWORD_MIN, and copy using that same constant. Validate length and match first, with the spec's messages. Then call `sb.auth.updateUser({ password })`. Map weak_password or same-password style responses (HTTP 422) to the plain fallback "That password can’t be used. Please try a different one." or a plain-words version. Do not show raw service text. A response meaning the session is too old or missing shows the "please sign in again" line with a link to login. A network failure keeps the form and shows the banner.
- Success shows "All set" with the "Go to my dashboard" link, focus to the heading, no auto-redirect, and both fields cleared.
- file:// shows the file card, and no SDK call. Run the session check again on `pageshow`, though a loaded token is not re-read.
- Never log, store or place the password or token anywhere else.

Dashboard: add a "Change your password" link to `set-password.html` near Sign out in the ready and empty states, as a plain text link (D-12, UI-spec amendment). There is no forced change on first sign-in, because no flag exists in the agreed schema. The marketer guide in 07-07 asks the client to change it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| email link to page | Query parameters are attacker-controllable and tokens are sensitive |
| page to Supabase Auth | Password and token sent over HTTPS through the SDK |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-30 | Information disclosure | Token left in URL, history or referrer | mitigate | replaceState before any await; `Referrer-Policy: same-origin` in 07-07; tested in `stub-setpass` |
| T-07-31 | Denial of service | Email scanner uses up the link | mitigate | Verify only on Continue click; tested by asserting no request on load |
| T-07-32 | Information disclosure | Account enumeration through reset | mitigate | Identical result for known and unknown addresses; live probe P2 |
| T-07-33 | Tampering | Forged `type` or `token_hash` values | mitigate | Allow-list on type; values used only as SDK arguments, never written to the DOM; server decides validity |
| T-07-34 | Spoofing | Hijacked session changing the password without the current one | accept | Prototype with fictional data per D-11; the XSS path is reduced by textContent and CSP. Noted for the real-data decision |
| T-07-35 | Repudiation | Misleading promise of email delivery | mitigate | D-12 copy with fallback; `reset-copy` guard rejects the unconditional sentence |
| T-07-36 | Information disclosure | Password in logs or URL | mitigate | POST through SDK only; `js` group forbids console.log; `stub-setpass` asserts no URL contains it |
</threat_model>
