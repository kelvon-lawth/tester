Rules for every plan in this phase:

- **Branch (structural push gate).** All Phase 7 work happens on the local branch `phase-07-client-login`, created from main. main stays where it is, so nothing can go live by accident. Only 07-08 touches main, and only 07-08 pushes anything, each behind its own approval. Executors must never merge to, commit to or switch to main outside 07-08. No pre-push hook is used.
- **Worktrees.** execute-phase runs each plan in an isolated `worktree-agent-*` worktree by default and merges it back with `--no-ff` onto whatever branch the primary checkout is on. So the branch must be current in the PRIMARY checkout, and `git branch --show-current` inside a worktree proves nothing. tools/assert-phase-branch.sh checks the primary checkout. Verify commands start with `cd "$(git rev-parse --show-toplevel)"` so they test the executor's own tree, not the primary checkout.
- **Credentials.** The agent never reads, cats, greps or copies `.env.local`. Live tests load it in-process through tools/auth-env.js and print no values. To check for credentials use `node tools/auth-env.js --check`, which prints names only.
- **Shell.** zsh is the shell. `timeout` and `gh` are not installed. An unquoted word starting with `=` is an error in zsh, so do not use `echo ====` as a separator.
- **Staging.** Stage files by explicit path. Never use `git add -A`, because `.claude/` and `.planning/phases/02-shared-shell-static-home/.continue-here.md` are untracked and must stay that way.

<task type="auto">
  <name>Task 3: Live RLS and sign-up test that cannot pass without running</name>
  <files>tools/auth-rls-test.js</files>
  <action>
Create tools/auth-rls-test.js using Node's global fetch, zero dependencies. Take the URL and publishable key from SUPABASE_URL and SUPABASE_PUBLISHABLE_KEY if set, otherwise parse them from js/auth-config.js. Take the test credentials through tools/auth-env.js load().

Exit codes: 0 means every case ran and passed. 1 means a case failed. 2 means it could not run. When any input is missing, print `LIVE TESTS NOT RUN: <names of what is missing>` and exit 2. Research suggested exit 0 here, but its own Validation Architecture says live tests must skip loudly and not pass, so a non-zero code is used so that a shell `&&` chain cannot move past it.

All output goes through one print function that throws if the text contains a value from secretValues(), an access token, or either test email. Report cases by label (signed-out, client A, client B) with HTTP status and row count. Never print tokens, passwords, emails or user ids. Never pass credentials in argv.

Cases, each by direct REST request against `client_dashboards`, sending `apikey` and, only when signed in, `Authorization: Bearer <access token>`:
- R1 positive control: client A signs in and an unfiltered read returns 200 with exactly one row whose user_id equals A's id from the token response. Same for client B (R2). Without these, an empty result elsewhere would prove nothing, so if either fails the run exits 1.
- R3 every visible row has is_sample true (D-11).
- R4 A filtered to `user_id=eq.<B id>` returns an empty array. R5 B filtered to A likewise.
- R6 signed-out read, unfiltered and filtered to A's id, returns no rows (401, 403 or an empty array). Any row is a FAIL.
- R7 a forged Bearer token returns no rows.
- R8 writes as A: POST a new row for B's id, PATCH own row, PATCH B's row, DELETE own row, DELETE B's row. Each must be refused or affect zero rows, using `Prefer: return=representation`. Re-read both rows after and compare to the first read, so a write that reported an error but still applied is caught.
- R9 signed-out POST, PATCH and DELETE, with the same re-read.
- S1 AUTH-06: GET `/auth/v1/settings` and record `disable_signup`. If it is true, POST `/auth/v1/signup` with a generated `@example.invalid` address and expect refusal. If it is not true, fail at once without attempting the POST, so no stray account or email is produced. If the POST ever succeeds, the failure message must tell the user to delete that account in the console.
- P1 to P3 are observation probes for research assumptions A3, A4 and A8. They print what was seen and only fail on a security problem: wrong password status and code, unknown-email recovery request status (same response as a known address, no enumeration), and an invalid `token_hash` on `/auth/v1/verify` status and code. The sign-in failure mapping in js must not depend on the printed code names, and the summary must record what was actually observed.

Use no retries that could hide a refusal. On HTTP 429 from the auth service, exit 2 with a message saying rate limited, try again in a few minutes, not a pass or fail.

Print a final table of case, label, status, row count and PASS or FAIL, in a form that can be pasted into evidence. The last line is `RLS OK` only when all cases passed. Only then does the test itself append `RLS-RUN | <today> | <git rev-parse HEAD> | RLS OK` to .planning/phases/07-client-login-dashboard/07-LIVE-EVIDENCE.md (creating the file if needed), with no emails, tokens or ids. On failure or missing credentials it appends `RLS-RUN | <today> | <sha> | NOT RUN` or `| FAILED`. No plan or person writes this line by hand.
