## Summary

The existing design (one `client_dashboards` row per client, `select`-only grant, `(select auth.uid()) = user_id` policy) extends cleanly. Add a `plan_tier` enum column to `client_dashboards` and put every Growth-only dataset in its own table whose single SELECT policy requires both `user_id = (select auth.uid())` and an `EXISTS` on the caller's OWN `client_dashboards` row with `plan_tier = 'growth'`. There is no recursion because `client_dashboards`' policy references nothing else. A Basics client calling `/rest/v1/content_calendar` directly gets `200 []` (RLS filters, it does not error), which is exactly what the test matrix should assert.

One trap the design must handle: the 6-month trend chart and the "this month vs last month" numbers come from the SAME monthly numbers. If the metrics table is readable by Basics, they can fetch 6 months directly. Solve it with a row-level window, not two tables: one `monthly_metrics` table (one row per client per month, columns `kpi1..kpi3`) whose policy lets Basics read only the reported month and the month before it (`report_month` stored on their dashboard row), while Growth reads all months up to `report_month`. The marketer enters each number once.

Everything is additive (new enum, new columns with defaults, new tables, no drops or renames), so the live deployed dashboard.js (which selects `steps`, `plan_name` etc.) keeps working during and after the migration. The chart is plain inline SVG built with `createElementNS` and attributes; this codebase already ships inline SVG with presentation attributes under the exact CSP and passes the CSP guard, and no `vercel.json` change is needed. The migration is applied with the Supabase Management API SQL endpoint using a user-supplied token (as in 07-04), and proven by an extended `tools/auth-rls-test.js`.

**Primary recommendation:** additive migration (enum `plan_tier`, 4 Growth tables with the EXISTS-on-own-row policy, `monthly_metrics` with the tier-dependent month window), seed A as basics with hidden Growth rows (so "0 rows" proves RLS, not absence) and B as growth, then rebuild dashboard.js around one embedded Basics read plus a second Growth read only when `plan_tier === 'growth'`.

### Pattern 1: Data model (exact SQL)

Run as one transaction. All statements idempotent where cheap. [ASSUMED: SQL not executed in this session (no psql/Docker here); first real execution is the live apply in Wave 1, so it must be followed by the verification queries.]

```sql
begin;

-- 1. Tier on the existing table. Default 'basics' = fail closed for any row not set explicitly.
do $$ begin
  create type public.plan_tier as enum ('basics', 'growth');
exception when duplicate_object then null; end $$;

alter table public.client_dashboards
  add column if not exists plan_tier     public.plan_tier not null default 'basics',
  add column if not exists report_month  date,   -- first day of the month the numbers describe
  add column if not exists next_check_in date,
  add column if not exists renewal_on    date,
  add column if not exists kpi1_label    text,
  add column if not exists kpi2_label    text,
  add column if not exists kpi3_label    text;

alter table public.client_dashboards
  add constraint report_month_first_day check (report_month is null or extract(day from report_month) = 1);
-- (wrap in a duplicate_object guard if re-runnable; the live apply runs once.)
-- Existing columns plan_name, plan_items, check_in, steps are KEPT (steps no longer read by the new page).

-- 2. Metrics: one row per client per month, three number columns. Entered once, used by
--    the at-a-glance card (Basics+Growth) and the trend chart (Growth).
create table public.monthly_metrics (
  user_id uuid not null references public.client_dashboards (user_id) on delete cascade,
  month   date not null check (extract(day from month) = 1),
  kpi1    numeric check (kpi1 >= 0),
  kpi2    numeric check (kpi2 >= 0),
  kpi3    numeric check (kpi3 >= 0),
  primary key (user_id, month)
);

-- 3. Waiting / done items (all clients).
create type public.item_kind as enum ('waiting', 'done');
create table public.dashboard_items (
  id         bigint generated always as identity primary key,
  user_id    uuid not null references public.client_dashboards (user_id) on delete cascade,
  kind       public.item_kind not null default 'waiting',
  title      text not null,
  detail     text,
  item_date  date,            -- waiting: due date (optional); done: date it was finished
  sort_order int not null default 0
);
create index dashboard_items_user_idx on public.dashboard_items (user_id);

-- 4. Growth-only tables.
create table public.content_calendar (
  id bigint generated always as identity primary key,
  user_id uuid not null references public.client_dashboards (user_id) on delete cascade,
  post_on date not null,
  channel text,               -- e.g. Instagram, Facebook, Newsletter
  title   text not null,
  status  text                -- free text, e.g. Planned, Needs your OK
);
create index content_calendar_user_idx on public.content_calendar (user_id, post_on);

create table public.ad_results (
  id bigint generated always as identity primary key,
  user_id uuid not null references public.client_dashboards (user_id) on delete cascade,
  month date not null check (extract(day from month) = 1),
  campaign text not null default 'All ads',
  spend numeric(10,2) check (spend >= 0),
  clicks integer check (clicks >= 0),
  results integer check (results >= 0),
  results_label text not null default 'enquiries'
);
create index ad_results_user_idx on public.ad_results (user_id, month);

create table public.report_archive (
  id bigint generated always as identity primary key,
  user_id uuid not null references public.client_dashboards (user_id) on delete cascade,
  month date not null check (extract(day from month) = 1),
  title text not null,
  url text not null check (url ~ '^https://')   -- blocks javascript: and http: links at the source
);
create index report_archive_user_idx on public.report_archive (user_id, month);

-- 5. RLS + explicit privileges on EVERY new table (Supabase may grant new tables to
--    anon/authenticated by default; remove first, exactly like schema.sql does).
do $$
declare t text;
begin
  foreach t in array array['monthly_metrics','dashboard_items','content_calendar','ad_results','report_archive']
  loop
    execute format('alter table public.%I enable row level security', t);
    execute format('revoke all on public.%I from public, anon, authenticated', t);
    execute format('grant select on public.%I to authenticated', t);
  end loop;
end $$;
-- identity sequences: clients never insert, so no sequence grants are needed.

-- 6. Policies. Basics-visible tables: own rows only.
create policy "clients read own items" on public.dashboard_items
  for select to authenticated using (user_id = (select auth.uid()));

-- Metrics: own rows, never past the reported month; Basics only the reported month and the one before.
create policy "clients read own metrics by plan" on public.monthly_metrics
  for select to authenticated
  using (
    user_id = (select auth.uid())
    and exists (
      select 1 from public.client_dashboards d
      where d.user_id = (select auth.uid())
        and d.report_month is not null
        and monthly_metrics.month <= d.report_month
        and (d.plan_tier = 'growth'
             or monthly_metrics.month >= (d.report_month - interval '1 month')::date)
    )
  );

-- Growth-only: own rows AND the caller's own dashboard row is growth.
create policy "growth clients read own calendar" on public.content_calendar
  for select to authenticated
  using (user_id = (select auth.uid())
    and exists (select 1 from public.client_dashboards d
                where d.user_id = (select auth.uid()) and d.plan_tier = 'growth'));
-- identical policy shape on ad_results ("growth clients read own ad results")
-- and report_archive ("growth clients read own reports").

notify pgrst, 'reload schema';
commit;
```

Why this is safe:
- **No recursion.** `client_dashboards`' policy is the unchanged `(select auth.uid()) = user_id`; the child policies query it (under the caller's RLS, which allows exactly their own row). No policy references its own table. Referencing the SAME table inside its own policy is what raises "infinite recursion detected in policy" [CITED: supabase.com/docs/guides/database/postgres/row-level-security, "policies that reference the table itself"], which is why the "latest two months" rule is driven by a stored `report_month`, not `max(month)` over `monthly_metrics`.
- **`(select auth.uid())`** wrapping makes Postgres evaluate it once per statement as an initPlan instead of per row [CITED: Supabase RLS performance guidance]. `user_id` columns are indexed (composite PK or explicit index).
- **Clients stay read-only.** Only `grant select`. No INSERT/UPDATE/DELETE privilege and no write policy exist; privilege check precedes RLS, so writes return 401/403 (as in R8/R9 today).
- **No self-upgrade.** `plan_tier` lives on a table clients cannot UPDATE. Add this explicit test (G7).
- **`report_month` null** (new client): the metrics policy returns nothing; the page shows "Your first numbers will appear here after your first monthly report."
- Growth client, `month <= report_month` also hides pre-staged future months; the marketer can enter next month early.

### Pattern 2: Seeding and the "0 rows proves nothing" trap

Seed client A (basics) WITH rows in all four Growth tables and 6 months of metrics, and B (growth) with the same shape. If A has no Growth rows, "A reads 0 rows" passes even with a broken policy. ### Pattern 3: Locked cards without a leak

- Decide by `row.plan_tier === "growth"` strictly; anything else (missing, unknown, error) renders locked. Fail closed in display.
- Basics path makes NO request to `content_calendar`, `ad_results`, `report_archive` (assert via `stubCount(st, "/rest/v1/content_calendar") === 0` in the stub test). The chart's data (`monthly_metrics`) arrives in the first read, but RLS only gives Basics two rows; the chart renders only when `plan_tier === 'growth'`.
- The locked card is static copy plus a decorative skeleton drawn in CSS/inline SVG with constant fake shapes (no real numbers, no blurred real data). Label it "Growth plan" and add "Ask about Growth" as a `mailto:` link with a subject (Phase 8 swaps this for checkout). Text must say what it unlocks ("See the last 6 months of your numbers"). Not a disabled control; plain heading + paragraph + link, so keyboard and screen-reader behaviour is simple.
- Growth requests failing show "I couldn't load this section. Try again" inside that card only; do not reuse the locked UI for errors.

### Pattern 4: "Up 12% on last month" safely

`cur` = metric for `report_month`, `prev` = the row for `report_month - 1 month` (match by month string, never by array index: a missing month must not make the older row look like "last month"). Rules:

| Case | Text |
|------|------|
| cur null/missing | "No figure for this month yet" (no arrow) |
| prev missing/null | "First month we've tracked this" |
| prev = 0 and cur = 0 | "Same as last month" |
| prev = 0 and cur > 0 | "Up from none last month" (never a percentage, never Infinity) |
| cur = prev | "Same as last month" |
| prev < 10 | "Up 3 on last month" (absolute; percentages on tiny bases mislead: 2 to 3 is "up 50%") [ASSUMED rule, planner may drop] |
| otherwise | `pct = Math.round(Math.abs(cur - prev) / prev * 100)`; if pct is 0 show "About the same as last month"; else "Up/Down {pct}% on last month" |

Arrow glyph in an `aria-hidden` span; the words carry the meaning (WCAG 1.4.1). Style "down" neutrally (ink-soft, not error red): a drop in "calls" is information, and for a cost metric it would be good. Format with `Intl.NumberFormat("en-GB", {maximumFractionDigits: 1})`. All values via `textContent`, `Number.isFinite` checks (PostgREST returns `numeric` as a JSON number).

### Pattern 5: Inline SVG trend chart under the CSP

Current CSP (vercel.json): `style-src 'self'` (no `unsafe-inline`), `script-src 'self' 'sha256-...'`.
- **Blocked:** `style="..."` attributes and `setAttribute("style", ...)`/`cssText`. **Allowed:** per-property CSSOM (`el.style.setProperty`, as main.js already does) [CITED: MDN style-src-attr: individual property sets are not blocked, whole-attribute sets are]. SVG presentation attributes (`stroke`, `fill`, `points`, `d`, `viewBox`, `width`, `height`) are not the `style` attribute; the Home page already ships inline SVG with attributes and `check-auth csp`/`auth-browser-test csp` passed with no violation on those loads [VERIFIED: 07-LIVE-EVIDENCE + index.html]. Browser consensus on presentation attributes is not spelled out in the sources I found, so the CSP stub group must load dashboard.html with a Growth row and fail on any violation (existing `dashboard@width` loop does this once the stub row is Growth) [MEDIUM].
- **Recipe:** colours, stroke widths and fonts come from CSS classes in `styles.css` (`.dash-chart__line`, `.dash-chart__dot`, `.dash-chart__label`) using existing tokens (`--color-blue`, `--color-coral`, `--color-ink-soft`); the JS sets only geometry attributes (`points`, `cx`, `cy`, `x`, `y`, `viewBox`) and `class`. Never set `style`.
- **Layout:** three small multiples (one tiny chart per KPI, each with its own y-scale), because the numbers have different magnitudes (calls ~40 vs visits ~900); one shared axis would flatten two of them. `viewBox="0 0 240 90"`, CSS `width:100%; height:auto`, so it scales on phones without JS resize. Up to 6 points, x evenly spaced by month index (gaps for missing months by month position, polyline broken into segments), y from 0 (or min) to max with 10% headroom; guard `max === min` (flat line) and a single point (draw a dot only).
- **Accessibility:** `role="img"` plus `<title>`/`aria-label` generated from the data ("Phone calls, last 6 months: May 31, Jun 35 ..."). Show the latest value and month labels as real text beside the chart, not only inside the SVG.
- **No animation** needed (reduced-motion safe, no scripting cost). If one is wanted later, use `stroke-dashoffset` only, as the Home page does.
- Fewer than 2 months of data: show "Your trend will appear after your second monthly report" instead of an empty chart.

### Anti-Patterns to Avoid
- **Hiding Growth data only in the page.** The lock is RLS; a CSS/JS lock fails D-71-04.
- **Two metrics tables (current vs history).** Double entry; or Basics-readable history leaks the chart.
- **`select max(month)` inside the metrics policy.** Same-table reference, recursion error.
- **Policy `exists(...)` on `auth.users` or joins to `auth.jwt()` claims for tier.** A JWT `app_metadata` tier claim goes stale until token refresh, and the tier must be changed by hand in a table editor. Read the live row instead.
- **`new Date("2026-10-01")`** parses as UTC; in a negative-offset zone it shows the previous day. Parse `YYYY-MM-DD` by splitting, then `new Date(y, m-1, d)`.
- **Setting `style` anywhere** in JS or markup (CSP). Use classes and SVG geometry attributes.
- **A plan-tier check by `plan_name` text.** Free text, typo-prone.

## Common Pitfalls

### Pitfall 1: Seeding no Growth rows for the Basics client
**What goes wrong:** the RLS case "A reads 0 rows" passes vacuously. **Avoid:** seed A with full Growth data and 6 metric months; add a one-time service-role/Management-API count query recorded in evidence showing A has rows in each Growth table, plus an optional tier-flip check (set A to growth via API, A can read, set back).

### Pitfall 2: Default grants on new tables
**What goes wrong:** Supabase's default privileges can give `anon`/`authenticated` full DML on tables created in `public`; RLS then is the only barrier. **Avoid:** the explicit `revoke all ... grant select` loop above, and a verification query listing grants for all five tables (expect only authenticated SELECT).

### Pitfall 3: Policy returns 200 [] not an error
Basics direct calls return `200 []`, not 401/403. Assert `rows.length === 0` and status in {200,401,403,404} (the existing `noRows`), never "status >= 400".

### Pitfall 4: Metrics leak via `select=*` on the 6 months
Covered by the window policy; test that A gets exactly 2 rows with months `{report_month, report_month-1}` and B gets 6.

### Pitfall 5: Clock-dependent display vs deterministic seed
"Next 2 weeks" calendar filter uses the viewer's clock; fixed seed dates will fall outside it. Compute dates at runtime in stub tests; for live seed either re-date by SQL (`current_date + n`) at seed time and accept drift, or have the live test assert only structure (card present). Format `today` from local components, not `toISOString()` (UTC shift near midnight).

### Pitfall 6: Existing guards that will break (must be updated in the same plan)
- `tools/check-auth.js` `groupDashboardPage`: forbids static "Sample Starter", "Sample step", "Hello,", "Your plan" in dashboard.html. - `tools/auth-browser-test.js`: `SAMPLE_ROW` (needs plan_tier, report_month, labels, nested `monthly_metrics` and `dashboard_items`), stub handler (the `/rest/v1/client_dashboards` route; add routes `/rest/v1/content_calendar|ad_results|report_archive`), `stub-dashboard` expectations (lines asserting "Your plan", "Next steps", "Sample date: this week", "Choose five photos you like." and the regex `/Hello,|Sample|Your plan|Next steps/` for the loading state), pageshow/back checks that grep "Sample Starter Plan", and `live` (`gridText` assertions "Hello, Sample Alex"/"Sample Blake"). `AUTH-04` wording ("welcome, their plan and next steps") must still be true: keep a compact "Your plan" card; "Next steps" becomes "Waiting on you".
- `tools/check-contrast.js` / `check-design-system.js`: new CSS must use existing tokens; new text/background pairs get checked.
- `tools/auth-rls-test.js` R8 posts `Object.assign({}, rows(readB)[0], ...)` so new columns flow through automatically; R3 asserts `is_sample === true` on rows (child tables intentionally have no `is_sample`; the parent flag covers the sample tag).

### Pitfall 7: Page weight and Home/Contact isolation
The weight budget is measured on Home's first view (403KB desktop / 362KB phone of 500KB at 911b34d) and only `css/styles.css` is shared with Home. Keep CSS additions small (file is 66.8KB now); put all new logic in `js/dashboard.js` (loaded only by dashboard.html, ~7KB now, expect ~20-25KB). Do not touch `main.js`. ### Pitfall 8: Marketer friction (user_id on every child row)
Each child row needs the client's `user_id` UUID. ### Change text (pure function, unit-testable by the stub tests)
```javascript
function changeText(cur, prev) {
  var n = function (v) { return typeof v === "number" && isFinite(v); };
  if (!n(cur)) return { arrow: "", text: "No figure for this month yet" };
  if (!n(prev)) return { arrow: "", text: "First month we’ve tracked this" };
  if (cur === prev) return { arrow: "→", text: "Same as last month" };
  var up = cur > prev;
  var word = up ? "Up" : "Down";
  if (prev === 0) return { arrow: "↑", text: "Up from none last month" };
  if (prev < 10) return { arrow: up ? "↑" : "↓", text: word + " " + fmt(Math.abs(cur - prev)) + " on last month" };
  var pct = Math.round(Math.abs(cur - prev) / prev * 100);
  if (pct === 0) return { arrow: "→", text: "About the same as last month" };
  return { arrow: up ? "↑" : "↓", text: word + " " + pct + "% on last month" };
}
```

### Sparkline geometry (no style attribute)
```javascript
var NS = "http://www.w3.org/2000/svg";
function spark(values /* up to 6, null for gaps */, w, h) {
  var svg = document.createElementNS(NS, "svg");
  svg.setAttribute("viewBox", "0 0 " + w + " " + h);
  svg.setAttribute("class", "dash-chart");
  svg.setAttribute("role", "img");
  var nums = values.filter(function (v) { return v !== null; });
  var max = Math.max.apply(null, nums.concat([1])), pad = 8;
  var seg = []; var cur = [];
  values.forEach(function (v, i) {
    if (v === null) { if (cur.length) seg.push(cur); cur = []; return; }
    var x = pad + i * ((w - 2 * pad) / Math.max(values.length - 1, 1));
    var y = h - pad - (v / max) * (h - 2 * pad);
    cur.push(x.toFixed(1) + "," + y.toFixed(1));
  });
  if (cur.length) seg.push(cur);
  seg.forEach(function (pts) {
    if (pts.length > 1) { var p = document.createElementNS(NS, "polyline"); p.setAttribute("points", pts.join(" ")); p.setAttribute("class", "dash-chart__line"); svg.appendChild(p); }
    else { var c = document.createElementNS(NS, "circle"); var xy = pts[0].split(","); c.setAttribute("cx", xy[0]); c.setAttribute("cy", xy[1]); c.setAttribute("r", "3"); c.setAttribute("class", "dash-chart__dot"); svg.appendChild(c); }
  });
  return svg;
}
```
